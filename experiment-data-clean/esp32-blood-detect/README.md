# ESP32 Blood Detection — XGBoost Run 6

Real-time, on-device version of the deployed model: a 1 Hz sensor loop that runs the
feature pipeline, the XGBoost tree model, and the causal EMA smoother entirely in C — no
external ML library on the device. It predicts **every second** from the trailing 60 s
window (sliding window), matching `test_exported_model.py` test 2.

## How it runs

The device samples at 1 Hz **continuously** and prints every reading — there is no start/stop
mode. The button sets the baseline, looking **backward** at the history already collected:

```
power on ──> reading + printing, history accumulating ──> [BUTTON] ──> classifying
             (no baseline, monitor only)                  fits baseline
                                                          from history
```

Press the button after the trace has settled in clean air (at least `BASELINE_MIN_S`, default
120 s; longer is better for the drift fit). It fits the baseline from up to the last 600 s of
filtered history, then classification begins — the first prediction comes 60 s later, once a
full window of baseline-corrected data exists. Pressing again re-fits from newer history.

Serial output is one line per second:

```
[247s] 0.3512 0.1403 0.1201 0.005 1.420 45.2   | blood     98%  (b 0.01 / s 0.01 / bl 0.98)
[123s] 0.0004 0.0002 0.0001 0.000 0.050 40.1   | filling window 43/60
[ 47s] 0.5094 0.3047 0.2023 0.100 0.050 40.0   | no baseline (47 s history)
```

## Filtering

The offline training pipeline (`mems_filter.ipynb` / `spec_filter.ipynb`) and what runs
on-device (`filters.h`):

| Channel | Training | On device | Match |
|---|---|---|---|
| `voc`, `nh3`, `hcho` | EMA span 30 | EMA span 30 | exact (EMA is causal) |
| `h2s_ppm`, `etoh_ppm` | Savitzky-Golay(121,3) → Butterworth(4, 0.005 Hz) | Butterworth(4, 0.005 Hz) | Butterworth exact, SG omitted |
| `rh_pct` | EMA span 60 | EMA span 60 | exact |

The Butterworth is the same order-4 design applied forward only (matching the notebook's
`lfilter`), implemented as two biquad sections in double precision; verified against
`scipy.signal.lfilter` to **4e-08**. The Savitzky-Golay stage is *centered*, so it needs 60
future samples and cannot run in real time. It is omitted — the Butterworth is far more
aggressive (0.005 Hz ≈ 200 s time constant) and dominates the result.

**Baseline correction**, also mirroring training:

- **MEMS** — least-squares **linear drift trend** fitted over the history window, subtracted
  and clipped at 0. This is the drift correction from `mems_filter.ipynb`, and it is why the
  button looks backward instead of sampling one instant.
- **SPEC** — constant offset (mean of the last 120 s of history), subtracted and clipped at 0,
  matching the stabilization-point offset in `spec_filter.ipynb`.
- **Humidity** — used as-is, uncorrected.

Tunables live at the top of `filters.h` (`BASELINE_HIST_S`, `BASELINE_MIN_S`,
`SPEC_OFFSET_TAIL`, EMA spans).

## Verified correct

`gen_headers.py` checks the emitted C logic against xgboost on the host before writing the
headers (it asserts and refuses to ship on mismatch):

- **Model:** C `xgb_predict_proba` (replicated in Python) vs `model.predict_proba` → max
  difference **6.4e-07** (float precision) on the held-out windows.
- **Features:** the causal `feat_push` / `feat_window` pipeline mirrors the Python window
  features; re-verify with the featverify template if sensors or preprocessing change.

So if `read_sensors()` feeds the right values, the device reproduces the notebook's predictions.

## Sensors — already wired

`main.cpp` reads the 6 channels using the same pins, ADC setup, and HDC302x as the
data-collection firmware (`src/main.cpp`), in the model's channel order:

```
[0] voc   [1] nh3   [2] hcho   [3] h2s_ppm   [4] etoh_ppm   [5] rh_pct
```

Each raw read is the mean of 64 ADC samples. **SPEC PPM** (`h2s_ppm`, `etoh_ppm`) uses the
**training** constants — including the H2S `×1.5` scale and EtOH `+0.100` offset that the
logger's `calcSpecPPM` leaves out. Filtering and baseline correction are described above.

## Preprocessing parity (read this — still the real risk)

The filter chain and the drift-corrected baseline now match training (see *Filtering*), so the
remaining gaps are smaller than they were, but they are not zero:

- **Savitzky-Golay stage is missing** on the SPEC channels because it is non-causal. The
  Butterworth dominates, but the two are not identical during fast transitions.
- **Filter settling.** The Butterworth has a ~200 s time constant and starts seeded at the
  first sample, so the SPEC channels need a few minutes before they track properly. Do not
  capture the baseline immediately after power-on.
- **Baseline window differs.** Training fitted the drift over a hand-picked pre-sample window
  (300–1300 s depending on session); the device fits over whatever history it has, up to 600 s.
- **Artifact windows** (manual spike removal in `mems_filter.ipynb`) have no device equivalent.

**Before trusting the device:** record one session on the ESP32 (raw Vgas/Vref + MEMS
voltages), run it through the Python pipeline, and confirm the 288 features match — the host
parity test (`featverify`) is the template.

## Build

**PlatformIO**
```
cd esp32-blood-detect
pio run -t upload          # build + flash
pio device monitor         # 115200 baud
```

**Arduino IDE** — open `main.cpp` (folder name matches the sketch), select an
ESP32 board, upload, open Serial Monitor at 115200.

## Resource use

- Trees compile to ~115 KB flash (5661 nodes).
- RAM: ~20 KB feature buffers + ~14 KB baseline history (600 s × 6 channels) ≈ 35 KB. Comfortable on an ESP32.
- Inference (861 trees) + feature aggregation runs **once per second**; still microseconds at 240 MHz.

## Output & latency

Readings print from power-on. Predictions begin 60 s after the baseline is captured, then one
per second. `EMA_ALPHA` (default **0.2**) sets the per-second smoothing — raw per-second
predictions were already ~100% in test 2, so a light EMA is enough; lower it for steadier
output, raise it for a snappier switch at the transition.

End-to-end latency from sample introduction to a confident call is dominated by the 60 s
feature window, not by inference.

## Regenerating the model

`xgb_model.h` and `feature_spec.h` are generated from `../model_export/` (produced by the
export cell in `combined_no_mix140.ipynb`). Re-export there, then:

```
../../.venv/bin/python3 gen_headers.py
```

It parses `xgb_run6.json`, emits both headers, and runs the host parity check (asserts
< 1e-4 before writing). Rebuild and re-flash afterwards.
